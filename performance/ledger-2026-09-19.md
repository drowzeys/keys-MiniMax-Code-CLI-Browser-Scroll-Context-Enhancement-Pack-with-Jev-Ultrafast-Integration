All numbers below come from **the runtime's own accounting**, not from marketing
materials: the `local_runtime_token_usage` table in
`~/.minimax/v2/sqlite/runtime-state.sqlite` (read-only query, `ts` is in
milliseconds), plus timed adversarial probes against the local vLLM endpoint.
Reproduce everything with `collect-usage.py` in this directory.

vLLM serving **GLM-5.3-EXL3 3.0 bpw (abliterated)**, TP=4 across 4× NVIDIA DGX

## How to actually validate an agent's performance claims

This section answers "people say MCode's performance is not as good as it claims
vs Codex / Claude Code / Hermes — how do you prove it?" Three instruments, each
measuring something different:

1. **The harness's own ledger** (what `collect-usage.py` reads). Measures real
   request counts, token volumes, and cost for *your* workloads on *your*
   stack. Not comparable across products unless you normalize per task.
2. **Timed adversarial probes** at known sizes (prefill X tokens, request
   Y concurrently, etc.). Measures the *serving stack* — prefill/decode rates,
   admission limits, failure modes. This is what exposed the compaction root
   cause. Bias: synthetic prompts, no tool loop.
3. **Fixed task-suite, harness-vs-harness**: same repo, same tasks, one run per
   agent, scored by tests passing / diff quality / wall time / tokens. This is
   the only instrument that measures the *product claim* end-to-end. Bias:
   suite selection and scorer design; publish the suite and raw transcripts or
   it's marketing.

Rule of thumb: a claim without (1) or (3) published is unverifiable; a vendor
tok/s number without (2) tells you nothing about your hardware.

## Reproduce

```bash
python3 collect-usage.py --day 2026-09-19   # per-session + totals
python3 collect-usage.py --totals-only
```

Read-only sqlite access (`mode=ro`). If the per-day filter returns nothing on a
different install, check the `ts` units first — this ledger stores milliseconds.
